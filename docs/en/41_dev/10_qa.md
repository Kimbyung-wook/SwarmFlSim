## 10.1 Running

Finish the C++ build and `uv sync` first.

```bash
uv run --with psutil python qa/run_qa.py --list
```

```bash
uv run --with psutil python qa/run_qa.py --only 001,010
```

| Option | Meaning |
|---|---|
| `--list` | List of tests |
| `--only <number,...>` | Run only some. All if absent |
| `--build-dir <dir>` | C++ build directory |

Results go to `qa/out/<TC>/` (process logs, MCAP, `.pb`) and `qa/out/results.json`.

## 10.3 Determinism diagnostics

Runs the same scenario several times in lockstep and compares the trajectories.

```bash
uv run python qa/diag_determinism.py --frames 3000 --seed 7 --runs 2
```

| Option | Meaning |
|---|---|
| `--scenario <file>` | Target scenario |
| `--frames`, `--seed`, `--runs` | Number of frames, seed, number of repetitions |
| `--verbose` | Verbose output |

Check changes that affect lockstep with this diagnostic ([chapter 9](09_contributing.md)).

To compare `LinkOutcome` and GCS receptions as well, use `qa/gw_plan.py --lockstep-det`. It repeats a same-seed lockstep run and compares the first 60 s with run 1.

```bash
uv run python qa/gw_plan.py --lockstep-det qa/out/det --det-runs 8 --variants noloss,loss,fault_noloss,fault_loss,payload
```

## 10.5 Performance measurement

The P1 performance condition is 10× or more with 3-DoF 100 vehicles waypoint, lockstep at maximum rate (`--rate 0`), Logger on and one Agent (DEC-082, DEC-084). P1 was judged complete under this condition (DEC-087, 12.43×). The tools are `qa/perf_p1.py` (full-stack rate and frame breakdown, with Logger on, split Agents, `--state-period 0` and Agent profiling setups) and `qa/perf_agent.py` (Agent cost alone). Results go to `qa/out/perf/` (excluded from git). Conditions and results are in [21_qa_report.md §29 and §31 to §34](../../21_qa_report.md#34-26차-측정-p1-판정-재측정-dec-086-개선-뒤-2026-11-15) (Korean).

### Judging method (DEC-086(2))

Performance judgments and performance regression judgments use the following method (DEC-087 keeps it in use).

| Item | Method |
|---|---|
| Window | Long window (7,500 frames for the judging setup). Short windows are for reference only |
| Batches | Two batches at different times of day. Round 26 took a one-hour break before the second batch |
| Representative value | Median of 6 or more runs |
| Paired value | Record the Logger-off value from the same run. Logger cost is Logger on minus off in the same round and scheduling |
| Run record | Keep each run's value with an E-core placement mark. An E-core run is one where more than 40% of system CPU was on logical cores 16 to 31 (O-42) |
| Cross-check | Also measure the setup pinned to P cores |
| Build | release, `-DSWARM_REQUIRE_ZENOH=ON` ([2.2](02_build_test.md#22-c-core-dynamics-datalink-logger-payload-bus)) |

- The same setup varied by up to 17% at different times of day (O-40). Do not judge from a single run. E-core runs dropped to 3.9 to 7.9×.
- Do not start the simulator on a PC where another measurement is running. In round 26, before each step, QA confirmed that no simulator process from another worktree had run for 30 s.

### Agent tick profiling (IMP-AGT-042)

To see where the Agent spends its time, pass `swarm-agent --profile <file>` or set the environment variable `SWARM_AGENT_PROFILE=<file>`. It is off by default, and with it on the bus output is byte-identical (TC-AGT-128).

- It times the tick-processing stages (MA, FA, activity reports, control publishing, FrameDone and so on) and the input handling between ticks (by key kind) with the wall clock.
- It sums them by frame phase (`frame % 50`, the position within the 1 Hz period). The first 250 ticks are dropped.
- The result is JSON, overwritten every 500 ticks and on close, so it survives a forced kill. `summary` holds ms per frame for phase 0, phase 4, the rest and all.
- The profiling setup of `qa/perf_p1.py` saves results as `agent-N_profile.json`. The round 26 breakdown is in [QA §34.5](../../21_qa_report.md#34-26차-측정-p1-판정-재측정-dec-086-개선-뒤-2026-11-15) (Korean).

## 10.7 Standards conformance check

The application of UCI, A-GRA, OMS/LA-CAL and AMS-GRA is checked with the in-house tool [qa/conformance/](../../../qa/conformance/) (DEC-092). It does not replace official conformance testing.

| Document | Contents |
|---|---|
| [44_standards_conformance.md](../../44_standards_conformance.md) | Check criteria C1 to C7, limits (§4), tool use (§5), history rules (§6) |
| [45_standards_report.md](../../45_standards_report.md) | Latest report produced by the tool |
| [46_amsgra_applicability.md](../../46_amsgra_applicability.md) | Applicability of each AMS-GRA requirement (applicable, partial, not applicable, with reasons, DEC-093) |
| [47_conformance_history.md](../../47_conformance_history.md) | Run history, check condition change history, finding tracking (with resolution cause) |

These documents are in Korean.

- Before a check, build the msvc-release Core. If the contract proto changed, regenerate the code with `scripts/gen_proto.py` ([44 §5](../../44_standards_conformance.md#5-도구-사용)).
- Each run appends one line to `qa/conformance/history.jsonl`, and the tool reads it to produce `docs/47`. Do not edit either file by hand (DEC-095).
- If a verdict changed, use the check condition change history in `docs/47` to tell whether the cause is a criteria or tool change or a product change.
- C1 marks STD messages that only travel inside a vehicle as "outside Gateway scope (vehicle-internal)" and does not count them as failures (DEC-094). C5 judges external command state with the UCI Command-2 state machine (DEC-097).
- The round 33 check on 2026-11-20 (contract 0.20.0) passed C1 to C6, with C7 informational. C3 includes a cross-check of the UCI epoch (DEC-098).
- The A-GRA L1 DDS requirements are kept as a check limit. The middleware change is on hold (DEC-099, [44 §4](../../44_standards_conformance.md#4-한계)).
